PlaySense BLE Integration — Architecture

How BLE device data flows into the existing scoring pipeline

Data Flow: BLE Device → Scoring
🔵 PlaySense BLE Device
Sends JSON via BLE notifications:
{ piezos: [420, 0, 0, 0, 0, 0], mic: 1200 }
▼ BLE characteristic notification
📡 PlaysenseContext (new file: contexts/playsense-context.tsx)
App-level provider — manages BLE connection lifecycle
Persists across pages. Exposes: connect(), disconnect(), connectionStatus, lastReading
▼ lastReading consumed by hook
🎯 usePlaysenseOnsets (new file: hooks/use-playsense-onsets.ts)
Converts BLE readings → OnsetEvent[]
Maps piezo index → drum surface name using instrument config
OnsetEvent { timestamp, energy: 420, surface: 'quinto' }
▼ recentOnsets[] (same interface as useOnsetDetection)
⚡ useExerciseSession (modified: hooks/use-exercise-session.ts)
Dual-source pattern: reads from BLE or mic based on audioMode
const activeOnsets = audioMode === 'playsense' ? bleOnsets : micOnsets
▼ onset.surface passed to grading
📊 gradeSingleOnset() (modified: lib/play-sense/scoring.ts)
New param: detectedSurface. Checks if hit was on correct drum.
Wrong drum = miss. No surface expected = timing only (backward compat).

Instrument Mappings

Congas — 3 Piezos + Mic
Piezo 1→ Quinto
Piezo 2→ Conga
Piezo 3→ Tumba
Piezo 4-6→ Unused
Mic→ Reserved (technique detection later)
Timbales — 6 Piezos
Piezo 1→ Macho
Piezo 2→ Hembra
Piezo 3→ Campana
Piezo 4→ Cencerro
Piezo 5→ Jam Block
Piezo 6→ Cáscara

Key Principle: Dual-Source Pattern

Both useOnsetDetection (mic) and usePlaysenseOnsets (BLE) are always instantiated (React hooks can't be conditional). Based on audioMode, only one source's startListening() is called. The rest of the pipeline (metronome, scoring, backing track) doesn't care where onsets come from — it just reads recentOnsets[].
